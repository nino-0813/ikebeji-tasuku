# イケベジ 進行ボード

二宮・本間・ゴーダの3人で、イケベジの **マーケティング** と **システム** を止めずに回すためのタスク管理アプリ。

Next.js (App Router) + Supabase + Tailwind CSS v4。

---

## この道具が解こうとしている問題

打ち合わせで決めたことが進まない原因は、タスクの数ではなく **「いまボールが誰にあるか」が誰にも見えていない** こと。
だから機能を足すのではなく、次の3つを構造として埋め込んでいる。

| 仕組み | どう効くか |
| --- | --- |
| **担当者と期限が空のタスクは保存できない**（DBレベルで `not null`） | 「誰かがそのうちやる」タスクが物理的に作れない |
| **5日ステータスが動かないと自動で⚠️に浮上**（`status_changed_at` を基準に判定） | 放置が見えるので、催促のきっかけが人の記憶に依存しない |
| **打ち合わせ画面が「前回の宿題」から始まる** | 会議の冒頭で必ず答え合わせが起きる |

「相手待ち」を独立した列にしているのも同じ理由。自分の手を離れたタスクを「進行中」に置いたままにすると、
止まっていることに誰も気づけなくなる。

## セットアップ（初回だけ）

### 1. データベースを作る

Supabase の管理画面 → **SQL Editor** を開き、[`supabase/schema.sql`](supabase/schema.sql) の中身を貼り付けて Run。
テーブル作成・トリガー・RLS・メンバー3人の登録までこれ1回で終わる。何度流しても壊れない。

### 2. `.env.local` を書く

`.env.local.example` をコピーして `.env.local` を作り、3行を埋める。

```
NEXT_PUBLIC_SUPABASE_URL=https://hgsnmzudqvgznvagtapu.supabase.co
SUPABASE_SERVICE_ROLE_KEY=（Project Settings → API Keys → service_role）
APP_PASSWORD=（3人で共有する合言葉）
```

`service_role` キーはサーバー側でしか使わず、ブラウザには一切出ない。外部に共有しないこと。

### 3. 起動

```bash
npm run dev
```

http://localhost:3000 を開き、自分を選んで合言葉を入れる。

## 全体の形

```
長期目標          例）12月までに定期購入者を100人
  └ 短期目標      例）9月末までに60人（長期の中の区切り）
  └ プロジェクト   例）定期便のリニューアル / Google広告の立ち上げ
        └ タスク   例）見出し案を確認して採用案を決める（担当・期限つき）
              └ サブタスク
```

**プロジェクトは消えない。** 中のタスクが全部終わっても一覧に残る。同じプロジェクトから次のタスクが
また出てくるからで、終わったタスクだけが一覧から消えていく。
本当に終わった塊は、プロジェクト画面の「畳む」で一覧から外す。

## 画面

| 画面 | 使うタイミング | 何が見えるか |
| --- | --- | --- |
| **ホーム** | 毎朝 / 打ち合わせ前 | 目標の現在地、詰まっているタスク、プロジェクト一覧（クリックで中のタスクが開く） |
| **今日** | 作業を始めるとき | 今日やるものだけ |
| **Inbox** | 思いついたとき | とりあえず放り込む。あとでタスクに変える |
| **ボード** | 作業中 | 未着手 → 進行中 → 相手待ち → 完了。ドラッグで移動 |
| **打ち合わせ** | 会議中 | 前回の宿題の消化状況 → 議事メモ → 今回決まったこと |
| **目標** | 月1回 | 長期目標とその中の短期目標。「今日あるべき地点」との差が出る |

どの画面でも `n` キー、または左の **新しいタスク** で追加できる。

## 運用ルール（これを守らないと元のごちゃごちゃに戻る）

### 打ち合わせの進め方

1. **打ち合わせ** から新しい回を作る
2. 画面上部の「前回の宿題」を全員で見る。終わっていないものはその場で **期限を引き直す**（放置しない）
3. 議事メモは自動保存されるので、書きながら話す
4. 決まったことは、その場で「決まったことを足す」から **担当と期限つき** で入れる。持ち帰らない

### 日々の使い方

- 自分の手を離れたら **すぐ「相手待ち」に移す**。何を待っているかも書く（次回「誰に催促するか」が一目でわかる）
- ⚠️ に出たタスクは、動かすか・期限を引き直すか・やめるかを決める。**そのまま置かない**
- 目標は月1回、実績の数字を入れるだけ。遅れていれば「月いくら必要か」が自動で出るので、
  そこからマーケの打ち手を足す

### プロジェクトと目標の使い分け

- **長期目標** … 半年〜1年で到達したい数字。頻繁に動かさない（例: 定期購入者100人）
- **短期目標** … 長期の中の区切り。「今月末までにここまで」を置くと、遅れに早く気づける
- **プロジェクト** … しばらく続く仕事の塊。中のタスクが尽きても消さない
- **タスク** … 1人が数日で終わらせる単位。担当と期限が必須

新しくやることが決まったら、まず「どのプロジェクトの話か」を決める。
どれにも入らないなら、それは新しいプロジェクトかもしれない。

### 領域の分け方

- **マーケティング** … Web サイト、Google 広告、SEO、コンテンツ、定期便の訴求
- **システム** … 顧客管理、機能追加、DB、管理画面まわり

## 構成

```
app/
  (app)/            ログイン後の画面（ホーム / 今日 / Inbox / ボード / 打ち合わせ / 目標）
  (app)/projects/[id]/   プロジェクト詳細
  login/            合言葉と「自分は誰か」
  api/tasks/[id]/   タスクのやり取り・サブタスク取得
components/         UI
lib/
  types.ts          ステータス・領域・停滞判定日数（STALL_DAYS）の定義
  data.ts           サーバー側の取得
  actions.ts        Server Actions（作成・更新・移動）
  goal.ts           目標のペース計算
supabase/schema.sql      DB定義（丸ごと流せば最新になる）
supabase/migrations/     途中から足した分だけの差分SQL
proxy.ts            合言葉による入口のガード
```

DB のテーブルは全て `tm_` 接頭辞。RLS は有効で公開ポリシーを持たないため、
アクセスは必ずアプリのサーバー側（`service_role`）を経由する。

停滞とみなす日数を変えたい場合は `lib/types.ts` の `STALL_DAYS` を触る。
